## 確認済み

- 加工GGUFは最初のα=1版と4ファイルのSHA-256が同一。α=0.5・0.25の調整は打ち切った。
- 書き込まれた18本を別実装のgguf-pyでも逆量子化し、C実装との差が全要素ゼロ。DeltaNetの列順も明示的な列インデックスで別に確認した。対象外バイト・構造は元Unslothと一致する。根拠は加工プロジェクトの `reports/written-weights-independent.json` と `reports/variants/a1-restored/assembly.json`。
- Gufoではα=1の英語の算術・順序問題は成功し、猫の説明も反復せず終了した。一方、日本語の簡単な算術はthinking有効・上限1536トークンでも反復して最終回答が空になった。入力全般で破綻するという結果ではない。記録は Gufoでの追加試験（ローカル保管：../luni-gufo-diagnosis-20261106/runtime-result.json）。

## 参照エンジン

Gufo公式flakeが固定するllama.cpp `68d9053afd4f4d0752ced6187585f862355a40be` を変更せず、既存GCC16.2・HIP clang24・ROCm10.1で `llama-server` のみビルドした。モデルは同じ固定Unslothを入力にする。ビルド来歴は build-provenance.json（ローカル保管：build-provenance.json）。

最初の短い制限時間では未加工モデルの読み込みが終わらなかったが、その後の延長試験で両モデルの推論比較まで完了した。自動読み込みは600秒、明示mmap・ストリーミング読み込みは各180秒で打ち切った。後二者は試験コンテナだけを12GiB・4CPUに制限した。グローバル設定への変更ではない。

小規模HIP転送はdefault stream・per-thread stream・イベント付きの3方式すべて成功した。各32回×1MiB転送と4MiBの読み戻しのバイト一致を確認。これだけで実モデル全体の転送を保証しない。記録は transfer-probes/results.json（ローカル保管：transfer-probes/results.json）。

デバッガで実モデルを約60秒動かした時点の主スレッドは、`llama_model_loader::load_all_data` → `read_raw_unsafe` → `fread` → `read` 内にあった。単一時点の観測であり、デッドロックやGPU待ちと断定しない。記録は 主スレッド（ローカル保管：load-debug-direct/main-thread.txt） と 全スタック（ローカル保管：load-debug-direct/gdb.log）。GDBの初回起動はイメージ内に `/bin/sh` がなく失敗し、シェルを使わない直接起動に直して取得した。

初回参照試験では、中断が後処理に重なり通常Gufoの自動復旧が実行されなかった。これを報告して同一コンテナを手動起動し、設定一致・ready・日本語応答を確認した。その後、ユーザーから調査中の停止継続を許可された。失敗を成功扱いせず、各試行の記録を残す。

ストリーミング読み込みの記録を再確認すると、約34秒の1.26GBから約169秒の8.38GBへディスク読み込み量が増えていた。停止という初期判断を訂正し、進捗を観測しながら上限1800秒で比較試験を開始した。小規模な通常メモリ・HIP固定メモリ・coherent固定メモリへの32MiB読み込みはすべて成功した（記録（ローカル保管：file-read-probes/results.json））。
