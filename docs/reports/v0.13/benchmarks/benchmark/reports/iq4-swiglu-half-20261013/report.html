−0の原因と、同じ値を保つ対策

2026年10月13日 / Gufo v0.13.0系ローカル改修 / Strix Halo gfx1151

対策は可能。実際のGufoカーネルを使った検査で、1,556,811組すべてが旧処理とビット一致しました。
公式で既に使われている Materialize をFP16変換の直前に使い、FP32の丸めをレジスタ内に残します。通常稼働には未適用で、速度・実モデル全体の評価は未実施です。

何が原因だったか

今回の本番相当HIPコンパイル条件は -O3 -ffast-math -fno-finite-math-only です。FP32でSwiGLUを計算して保存する旧処理と、直ちにFP16へ変換する SwigluHalf は、ソースの式が同じでも最終的なGPU命令が異なりました。

経路実際の最後の処理違い
旧処理：Swiglu → NarrowActivationsFP32掛け算 → FP32保存 → 別カーネルでFP16変換FP32で一度丸める
対策前の直接出力v_fma_mixlo/hi_f16：掛け算＋正の0、FP16結果FP32の中間丸めが省略され、−0の符号も変わる
対策後の直接出力v_mul_f32 → v_cvt_f16_f32旧処理の丸めを残し、FP32のメモリ保存を省く

たとえば gate = −0、up = 0.217899 では旧処理のFP16値は 0x8000（−0）、対策前の直接出力は 0x0000（＋0）でした。融合命令に含まれる ＋0 が符号を変えます。

追加調査では、−0以外に14組の丸め差も見つかりました。一例では旧処理のFP32値が34.515625になり、FP16への偶数丸めで34.5（0x5050）になる一方、直接出力は34.53125（0x5051）になります。したがって、最後にゼロの符号だけを戻す処置では不十分です。「−0だけの問題」という前の説明を、この調査結果で補足します。

単独のFP32→FP16変換では不一致が0件だったこと、実Gufoカーネルでも再現したこと、実際の生成命令、修正後の一致を合わせて原因を特定しました。生成命令の抜粋 / 対象カーネルの全アセンブリ

対策の内容と範囲

Gufoには既に Materialize(float) という補助関数があります。コンパイラによる前後の計算のまとめ直しを抑え、FP32の値を確定させる目的の処理です。同じ補助関数を、SwiGLUの最終積だけに適用しました。

float value = SiluF(gate) * up;
value = Materialize(value);  // 既存のFP32丸めを残す
out = __float2half(value);  // FP16へ直接出力

Materialize 自体はレジスタを対象とする空のインラインアセンブリで、GPU全体の同期やメモリへの書き戻しを追加するものではありません。生成命令でも、修正経路の v_fma_mix が消え、FP32積とFP16変換が分かれていることを確認しました。

SiluFの途中まで強制的に確定させる方法も試しましたが、それでは旧処理の最適化済みの計算順序と変わり、6組で非ゼロ値の不一致が残りました。採用候補は最後のFP32値だけを確定させる方法です。

変更点今回の試作
内部カーネルSwigluHalfKernel<PreserveF32> と SwigluValue を使用。テンプレートで処理を分け、要素ごとの実行時条件分岐を追加しない。

実行経路への接続未接続。A案の実行部分も今回変更していない。検証用の独立ブランチに保存。

本体に近づくか、採用する合理性はあるか

データの流れは、公式のQ8向け処理に近づきます。参考元はAと同じ、Gufo公式の 共有エキスパート用のFP16バッファを分離した変更です。既存の関数・補助処理・専用バッファを再利用できます。

現在のA候補：SwiGLU → FP32を保存 → 別処理でFP16変換 → shexp_half
今回の対策案：SwiGLU → レジスタ内でFP32値を確定 → FP16を直接shexp_halfへ

実行経路に接続できれば、Aが既に省いた再変換に加えて、共有エキスパートのFP32中間値の書き込み・読み込みと変換カーネル1回を省けます。4096行×640要素なら1層につき書き込み10 MiB＋読み込み10 MiBという論理上の転送量です。実際のDRAM転送量や処理時間を計測した値ではありません。

一方、融合命令を避ける分だけ演算命令は増えます。転送と起動回数の削減がどこまで上回るかは実モデルで測る必要があります。また、Aのバッファ接続だけの変更と比べると共通カーネルへの拡張が増えるため、公式更新時には既存呼び出しの一致検査を継続する必要があります。

判断：この修正を次の採用候補として優先して検証する合理性があります。ただし、ここで確認したのは演算単位の同一性と原因の解消です。実モデルの生成結果・MTP・Prefill/TTFT/Decodeの速度は未評価のため、本採用済みとは扱いません。以前のAの速度表をこの案の実績として流用もしません。

通常運転のGufoはbaseline 9bbd97fのまま、正常応答を確認。Aも今回の対策案も未採用。Strataは起動していません。
