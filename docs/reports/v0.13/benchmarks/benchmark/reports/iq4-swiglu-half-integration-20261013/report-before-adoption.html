Gufo v0.13.0 / Orca IQ4_XS
修正版A：丸めを保つFP16直接出力

2026年10月13日・Strix Halo gfx1151 / WSL / Docker

IQ4の共有エキスパート経路へ、検証したFP16直接出力を接続しました。
既存の専用バッファを再利用し、FP32中間値の保存・読み出しと別の変換カーネルを省きます。FP32で一度丸める境界はMaterializeで保持しています。通常運用は採用判断前の構成へ復旧しています。
判定：精度・動作は合格。128K Decodeの平均低下と個別の遅延増が残るため、速度面の採用は保留。

実装の内容

変更したのは、prefill_phaseかつ共有down重みがIQ4_NLである既存のA分岐です。Orca IQ4_XSモデルの該当テンソルがこの条件に入ります。形状などの既存ガードは維持しました。

従来A
  Swiglu(...);                  // FP32をメモリに保存
  NarrowActivations(...);      // 読み直してshexp_halfへ

修正版A
  SwigluHalf(..., true, stream_); // FP32丸めを保持してshexp_halfへ直接出力

trueは内部の「FP32丸めを保つ」選択です。起動パラメータや環境変数は増やしていません。カーネルはテンプレートで特殊化され、要素ごとの実行時分岐を追加しません。既存Q8側の5引数呼び出しはそのまま残しています。

前回の原因調査で確認したとおり、単純な直接出力はコンパイラによる融合で−0や丸め結果が変わります。今回はGufo既存のMaterializeを最終FP32積にだけ適用し、値をレジスタ内で確定してからFP16へ変換しています。

公式Q8側と同じく、生成したFP16を専用のshexp_halfへ直接渡す流れです。重みの精度、行列積、バッファ容量、Decodeの分岐、Q4/Q8の演算は変更していません。4096行×640要素では1層につき論理上のFP32書き込み10MiB＋読み込み10MiBと変換カーネル1回を削減します。DRAM実測値ではありません。

精度・動作の検査

  • 実際のGufoカーネルで、1,556,811組のFP16中間値が旧処理とビット一致。−0、極小値、ランダム入力、末尾処理を含む。
  • IQ4共有downの1 / 8 / 9 / 32 / 33 / 129 / 257 / 4096行：FP16中間値と最終FP32出力が旧処理とビット一致。
  • 独立CPU FP64基準の相対RMSは2.0255×10⁻⁶。従来上限2×10⁻⁵を維持。既存native IQ4演算テストも合格。
  • 修正版を接続した実モデルで136 tokenを一括／127＋9に分割。選択した5位置の層別トレースに数値差なし。
  • 正式な32K・128Kの12応答で、生成文・入力数・出力数が従来Aと一致。MTPが実際に働いていることも確認。
  • 短文での2会話同時実行、seed固定のサンプリング再生成、別会話からのキャッシュ復帰を両構成で確認。

全入力の数学的同値証明、全モデルlogitと公式teacherの比較、同時128K×2会話の検証ではありません。許容誤差や基準の緩和はしていません。

個別の遅延判定

各回のPrefill、TTFT、Decodeごとに、5%超かつ3ms超の遅延増を確認します。平均で相殺せず、全測定を残します。

追加確認の生データと判断

本番バイナリのGPU命令も確認しました。対象翻訳単位の共通173関数のうち157関数はバイト同一、残る16関数はPC相対アドレスを参照先の定数へ解決すると同じ命令と定数でした。既存SwigluHalfの4要素まとめ処理は同じですが、端数用の分岐では待ち命令・スケジューリングに差があります。前回の出力一致検査に加える材料であり、全処理の速度同等性の証明ではありません。
