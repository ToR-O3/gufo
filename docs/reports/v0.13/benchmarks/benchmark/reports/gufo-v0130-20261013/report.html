3. 最新Strataから分かったこと

Strata v0.1.43の速度向上は、対象GPU・量子化形式・GPUに収まる重みの割合に依存します。目立つRDNA4向け変更はgfx1200／gfx1201が対象で、gfx1151へ同じ増加率を当てはめる根拠はありません。

Strataでの変更・着想Gufo / Orcaへの評価
HCの計算結果とQ8_1入力を同時に作るGufoにも生成側の仕組みがある。IQ4側で既存結果を受け取る接続が不足しており、下記B1の根拠になる。
正規化の入力をレジスタに保持Gufoは RmsNormCachedKernel で2560／10240幅を処理済み。共通処理を置き換える必要性は低い。
トークン・制御情報を固定メモリから転送Gufoにも固定メモリと転送完了を待つ仕組みがある。今回の新規移植候補から除外。
専門家の入替、PCIe転送の重ね合わせGPUに専門家の重みを保持する現在のGufo構成との前提が異なる。優先度は低い。
専門家の一部省略／INT8 Prefill／精度を変える高速設定回答や中間計算が変わるものがある。過去に不合格になった方式も含むため採用候補から除外。

Strix Halo文書はv0.1.42から変更されていません。掲載の51 tok/s前後は、Unslothのモデル、Linux環境、独自の高速設定で得られた数字です。文書自身が丸めの変わる設定を区別しており、現在のWSL・Orca・精度維持条件での到達保証値ではありません。

公式Gufoにも新しい不採用記録があります。8192トークンの入力チャンクは約3GiBの追加作業領域に対して明確な改善がなく、SSM処理の別ストリーム化も遅くなっています。今回これらを起動設定に追加しない理由です。Gufoの実験記録

4. 改善案：A → B1 → B2 → C

前回の優先順位は維持します。今回の公式更新ではIQ4側の接続不足は解消されていません。モデルファイル名はIQ4_XSですが、内部にはIQ4_NLなども含まれるため、実際のテンソル形式と形状を条件に限定します。

順番・狙い変更内容精度維持の条件
A：Prefill / TTFT
共有専門家の中間入力を再利用		Q8経路にあるSwiGLUの直接FP16出力を、IQ4_NL共有専門家のDownへ接続する。専用の既存バッファから NativeIq4DenseF16 に渡し、変換し直しと他の入力バッファの上書きを減らす。今も行うFP16への丸めの位置・回数・値を保つ。重みをFP16に展開する過去の失敗案とは別。SwiGLU後のビット列とDown出力を比較。
B1：Decode / MTP
作成済みQ8_1入力の再利用		HCがすでに作った mixed_q8_ready_ をIQ4_XSのGate/Upに渡す。今はIQ4の経路で同じ入力を再量子化しているため、その重複だけを省く。既存Decodeが使用するQ8_1コードとスケールが完全一致すること。FP16 PrefillをINT8方式へ変える改修ではない。Q4/Q8経路は維持。
B2：Decode / MTP
IQ4のGate/Up処理をまとめる		B1を単独で評価・採用した後、既存の融合処理にIQ4_XS専用の分岐と対応カーネルを足す。入力読み込み・起動・中間メモリの費用を減らす。単に条件を足すだけでは不十分。ドット積の足し順、SwiGLUの丸め、出力配置を元と一致させる。未対応の行数は従来経路へ戻す。
C：MTP中心・低優先
IQ4_NL Downの入力を専門家ごとにまとめる		既存のQ5_1/Q8_0用処理を参考に、同じ専門家を使う行をIQ4_NLでも近くに置き、重みの読み込みを再利用。最後に元の出力スロットへ戻す。重みの再量子化・全面並べ替えはしない。各行の演算と専門家の合算順を保持。並べ替え自体の負担で遅くなれば不採用。

変更はそれぞれ別コミットにし、Gufoの NativeIq4…、…_preq など既存の命名と設計に合わせます。共通ファイル内にIQ4専用の分岐を加える範囲に留め、Q4_K_XL側の処理や共通スケジューラー・キャッシュ方式の置き換えは提案しません。

Strataから取り入れるのは「作った中間結果をその場で利用する」「同じ重みを複数行で再利用する」「加算順を守る」という実装上の工夫です。現在のGufoの計算契約に合わせて実装する必要があり、Strataのカーネルをそのまま差し替える案ではありません。

5. 採用判断の条件

  1. 元の計算との一致に加え、独立した参照値を用いる既存の数値テストに合格する。しきい値は緩めない。異常値を黙って0に置き換えて通すこともしない。
  2. 最初に小さな数値テスト。その後、単独の変更について32K／128Kを各3回測り、平均と各回を保存する。悪化を平均で隠さず、ばらつく結果は保留する。
  3. 今回からsessions 2を前提に、同時実行時の状態混線、MTPの棄却・巻き戻し、固定seedでの再現、会話キャッシュ復元も短く確認する。1～8行だけでなく、同時実行から生じる幅と従来経路への戻りも対象。
  4. Prefillが速くてもDecode・TTFT・メモリの悪化がないか確認。精度不合格または明確な性能悪化は戻す。
  5. 結果を提示し、ユーザーが採用と判断した項目だけを残して次へ進む。

追加改善はすべて未実装・未測定です。改善率の予測値や、無劣化を確認済みという扱いはしていません。次に着手するなら、変更範囲の小さいAを単独で実施するのが妥当です。
