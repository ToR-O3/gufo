# Gufo v0.7.0 キャッシュ動作とメモリ使用のレポート

> 履歴資料：本文の採用状況・起動状態・未完了事項は作成当時の記録です。現在の仕様は共通カスタム台帳を参照してください。測定値は再集計せず保持し、個人ホームパスを匿名化しています。生ログ・個人設定は公開対象に含めていません。

作成日：2026年10月5日  
対象：Gufo v0.7.0／Qwen3.8-Flash-Next

このレポートは、キャッシュに関する相談内容を、公式ソースコードと仕様書の調査に基づいてまとめたものです。容量の数値は概算であり、この調査では実機測定や実行中サーバーの設定変更は行っていません。

## 1. キャッシュが短縮する処理

キャッシュの主な効果は、入力の再計算を省き、回答が始まるまでの時間を短縮することです。

保存されるのは計算式や回答文ではなく、入力を処理して得られたK/V、再帰状態などの数値データです。ある地点までの計算状態を保存したものを、以下では「チェックポイント」と呼びます。

| 処理 | 内容 | 保存キャッシュによる効果 |
|---|---|---|
| Prefill | 会話履歴や質問などの入力を処理する | 一致する保存地点までの計算を省ける |
| Decode | 回答を順次生成する | 生成速度そのものを直接引き上げる仕組みではない |
| TTFT | 要求から最初の出力までの時間 | Prefillを省けた分、短くなる |

例えばPrefill性能が1,000 tok/sなら、10万トークンの入力には概算100秒かかります。先頭9万トークンを再利用できれば、必要なのは残り1万トークンの処理約10秒と復元時間です。

したがって、キャッシュによってdecodeが25→40 tok/sになるというより、**25 tok/sで生成を始めるまでの待ち時間が短くなる**と考えるのが適切です。入力全体を処理時間で割った表示では、見かけ上のPrefill tok/sが上がるため、実際に計算したトークン数との区別が必要です。

出典：[公式の説明](https://github.com/gufo-org/gufo/blob/v0.7.0/docs/KV-CACHE.md#what-kv-cache-means-here)

## 2. 設定項目と上限の意味

キャッシュ関連の設定は、保持場所と用途が異なる独立した上限です。

| 設定 | 制限・指定するもの |
|---|---|
| `--cache-ram-bytes` | RAMに保持するチェックポイントと、作成中の予約容量 |
| `--cache-disk DIR` | SSDなどへの保存を有効にする保存先 |
| `--cache-disk-bytes` | ディスクに保持するファイルの合計容量 |
| `--cache-disk-staging-bytes` | ディスク保存用の待機・作成領域や、読み込み可能なファイルサイズ |

RAM上限を2GiBにしても、起動時にキャッシュ用として2GiBを全量確保するわけではありません。保存が必要になった際に増えます。

また、RAM上限にはモデルの重みや通常の推論状態、ディスク関連の一時領域などが含まれません。**サーバー全体のメモリ上限ではありません。**

`cache-ram-bytes 1`は追加の保存をほぼできなくしますが、生成中に必要な通常のKVキャッシュは動作します。直前の推論状態をそのまま使える場合の再利用も残ります。なお、`0`は無効化ではなく自動サイズ設定です。

ディスクの容量設定だけではSSD保存は有効になりません。`--cache-disk`による保存先の指定が必要です。

本レポートでは容量を原則としてGiBで記載します。1GiBは1,073,741,824バイトです。会話中の「2G」などは概念上の容量表現であり、その文字列をCLIが受け付けることを確認したものではありません。

出典：[容量設定の仕様](https://github.com/gufo-org/gufo/blob/v0.7.0/docs/KV-CACHE.md#limits)

## 3. RAMキャッシュが満杯になった場合

RAMが満杯になったときは、保存状態の用途と関係性を見て入れ替えます。保存・削除の単位はチェックポイント全体です。

削除順位は次のとおりです。数字が小さいものから削除し、同順位では最後に使われた時点が古いものを選びます。

| 削除順位 | 既存のチェックポイント |
|---|---|
| 0 | 別に継続用の復帰地点が残っている、再実行用の保存 |
| 1 | 関連する継続用の保存がある、入力処理途中の保存 |
| 2 | 同じ履歴をさらに先まで処理した保存がある、古い継続用の保存 |
| 3 | 上記に当てはまらない保存。会話に残された唯一の復帰地点など |

新しく追加する用途によって、削除できる範囲も変わります。

| 新規保存の用途 | 削除できる既存分 |
|---|---|
| 再実行用：`kRetry` | 順位0だけ |
| 途中保存：`kHistory` | 順位0・1 |
| 継続用：`kContinuation` | 順位0〜3 |

そのため、順位3だけが残っている場合、途中保存などの追加は見送ります。継続用の追加なら、削除可能な中で最終利用が古いものから、必要な個数を削除します。

同じ会話の更新では、自分の古い復帰地点を先に置き換える配慮もあります。複数の会話の分岐点は不要な古い保存と扱わず順位3にしますが、永久保存されるわけではありません。

順位は固定ではなく、ほかに保持している状態や追加する状態との関係で決まります。関連性はトークン列の先頭一致と入力識別情報で判定し、会話内容の意味を分析して重要度を付ける方式ではありません。

出典：[削除順位の実装](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/continuation_cache.cpp#L97)、[用途別の制限](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/continuation_cache.cpp#L27)

容量判定には、次の合計を使います。

```text
保存済み容量 ＋ 作成中の予約容量 ＋ 新規保存分
```

新規分が「上限−予約済み容量」に単独でも収まらない場合は、既存分を削除せず保存を見送ります。それ以外では、収まるまで削除候補を選び直して1個ずつ削除し、候補が尽きれば新規保存を見送ります。途中まで削除しても結局収まらなかった場合、削除済みの分を元に戻す処理はありません。

保存できなくても、それ自体を理由に推論を停止したり、入力の会話履歴を切り捨てたりする処理ではありません。後で必要になった部分は、利用できる以前の状態から、または入力の最初から再計算します。

出典：[容量確保の実装](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/continuation_cache.cpp#L735)

### 入れ替えの例

上限2GiBで、以下の3個を保持しているとします。容量は説明用の仮の値です。

| 現在の中身 | 容量 | 削除順位 |
|---|---:|---:|
| 会話Aの継続用保存 | 0.6GiB | 3 |
| 会話Aの再実行用保存 | 0.6GiB | 0 |
| 会話Bの継続用保存 | 0.6GiB | 3 |
| 合計 | **1.8GiB** | |

ここへ会話Cの継続用保存0.6GiBを追加すると、Aの再実行用保存を削除して、A・B・Cの継続用保存を各0.6GiB、合計1.8GiB残せます。

この後、新しく0.6GiBの途中保存を追加しようとしても、削除順位3しか残っていないため保存を見送ります。新しい会話Dの継続用保存なら、削除可能な中で最後の利用が最も古いものを削除できます。

出典：[対応する上流の単体テスト](https://github.com/gufo-org/gufo/blob/v0.7.0/tests/cli/continuation_cache_test.cpp#L549)

## 4. SSDキャッシュの保持と削除

SSDキャッシュは、RAMからあふれたものをすべて自動退避する仕組みではありません。

保存条件を満たすチェックポイントを別途ディスクへ書き込みます。RAMから削除された状態でも、SSDに保存済みなら復元できます。一方、保存対象や容量条件を満たさなかったものはSSDに残りません。

SSD側は、0.6GiB、0.8GiBなどのファイルを複数保持し、合計上限まで使います。次の保存で上限を超える場合は、**最後に使われた時点が古いファイルから削除**します。RAM側の用途別の削除順位とは異なります。

例えばSSD保存上限が16GiBなら、概念的には次のような保持になります。

```text
0.6GiB ＋ 0.8GiB ＋ 0.6GiB ＋ 0.9GiB ＋ …… ≦ 16GiB
```

復元時に読み込むのは、その中から選ばれた必要なチェックポイントです。保存済みの16GiB全部をRAMに読み込むわけではありません。

出典：[ディスクキャッシュの仕様](https://github.com/gufo-org/gufo/blob/v0.7.0/docs/KV-CACHE.md#the-disk-tier)

## 5. ステージングの意味

ステージングは、大きなファイルを小分けに処理するためのサイズ指定ではありません。

v0.7.0の復元処理は、対象ファイルを丸ごと一時RAMバッファへ読み込み、推論状態へ反映した後、そのバッファを解放します。したがって、ステージング1GiBで7GiBのチェックポイントを1GiBずつ読み込むことはできません。

保存時にもチェックポイントのコピーや書き込み待ち用のRAMを使います。こうしたディスク処理のメモリは、`cache-ram-bytes`とは別に考える必要があります。

出典：[読み込み処理](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/continuation_disk_store.cpp#L749)、[保存用の容量判定](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/continuation_disk_store.cpp#L695)

### RAM 2GiB／SSD 16GiB／ステージング1GiBの場合

管理情報や処理中の予約を省略すると、扱えるサイズは次のイメージです。

| チェックポイント1個の大きさ | RAM保存 | SSD保存・復元 |
|---|---|---|
| 0.6GiB | 可能 | 可能 |
| 1.5GiB | 可能 | ステージング上限を超えるため不可 |
| 2.5GiB | 不可 | ステージング上限を超えるため不可 |

SSDには1GiB未満の保存状態を多数、合計16GiBまで保持できます。ただし、すべてのチェックポイントが必ず保存されるわけではありません。

RAMとステージングを同じ値にする必要もありません。RAMは保存済み状態の**合計容量**、ステージングはディスク処理用の容量です。同等以上のステージングなら大きな状態も扱いやすくなりますが、その一時RAMを使える余裕が必要です。厳密にはディスクファイルの管理情報分も考慮します。

例えば、常時保存するRAMを抑えつつディスクを使う目的で、RAM上限を1バイト、ステージングを2GiBにする組み合わせにも意味があります。

## 6. SSD読み込みの発生条件とメモリ使用量

RAMが満杯であることと、SSDからの読み込みが発生することは別です。

| 今回の入力に再利用できる状態 | 動作 |
|---|---|
| 直前の推論状態、またはRAMキャッシュにある | RAM側を再利用 |
| RAM側になく、SSDにある | SSDから該当するチェックポイントを復元 |
| どちらにもない | 入力を再計算 |

v0.7.0ではRAM側で再利用できなかった場合にSSDを調べます。RAMとSSDを毎回比較して、最も長い保存状態を選ぶ実装ではありません。

出典：[再利用経路の実装](https://github.com/gufo-org/gufo/blob/v0.7.0/src/cli/serve/text_model_runner.cpp#L1730)

RAMに2GiB保持した状態で、SSDから0.8GiBを読むなら、この2つだけで一時的に約2.8GiBを使います。

```text
RAMキャッシュ 2GiB ＋ 読み込み用バッファ 0.8GiB
＝ この2つだけで約2.8GiB
```

モデル、通常の推論状態、その他の作業領域は別です。**RAM上限とステージング上限の合計が、サーバー全体や追加メモリ全体の厳密な上限になるわけではありません。**

同じ会話を続けて直前の状態を再利用できれば、毎回SSDを読む必要はありません。一方、RAMに収まらない複数の会話を頻繁に切り替える場合は、保存・復元が繰り返され、一時領域を使う状態が続く可能性があります。

バッファの解放も、Windowsの空き物理RAMが即座に同量戻る保証ではありません。実運用では待機時だけでなく、保存・復元を含む連続利用中の空きRAMを見る必要があります。

## 7. 1GiBで保持できる情報量の目安

Qwen3.8-Flash-Nextでは、1GiBは約3万〜4万トークン地点の状態を1個保存できる規模です。

以下は公式v0.7.0のモデル構造と保存形式から算出した、テキスト入力での概算です。実測値ではありません。管理情報やMTPの保存時点によって多少変わります。

| 保存地点 | MTPなし | MTPあり |
|---|---:|---:|
| 8K＝8,192トークン | 約0.30GiB | 約0.32GiB |
| 16K＝16,384トークン | 約0.50GiB | 約0.53GiB |
| 32K＝32,768トークン | 約0.88GiB | 約0.95GiB |
| 256K＝262,144トークン | 約6.30GiB | 約6.82GiB |

これは文章そのものの容量ではなく、計算状態の容量です。保存物ごとの固定部分もあるため、MTPありでは次の違いが出ます。

- 8K地点の状態を3個：約0.96GiBで、おおむね1GiBに収まる。
- 16K地点の状態を2個：約1.06GiBで、1GiBに収まらない。
- 32K地点の状態を1個：約0.95GiBで、おおむね1GiBに収まる。

この表は、その地点に保存候補がある場合のサイズです。**容量を1GiBに設定すると、自動的に収まる限界の約32K地点で保存してくれる、という意味ではありません。** 実際の保存地点は会話境界や入力処理中のチェックポイントなどによって決まります。

したがって、ステージング1GiBなら32K程度のチェックポイントは扱える目安ですが、256K地点の状態は扱えません。

出典：[モデル構造](https://github.com/gufo-org/gufo/blob/v0.7.0/src/models/qwen38_flash_next/config.hpp)、[保存サイズの計算](https://github.com/gufo-org/gufo/blob/v0.7.0/src/models/qwen38_flash_next/kernels/rocm/executor.cpp#L2161)、[ホスト側保存サイズ](https://github.com/gufo-org/gufo/blob/v0.7.0/src/models/qwen38_flash_next/engine.cpp#L307)

## 8. 運用条件ごとの設定の考え方

| 運用上の条件 | 設定を考える方向 |
|---|---|
| 追加RAMをほとんど使えない | RAM保存を小さくし、ディスク用の一時RAMも抑える |
| 少量のRAMには余裕がある | RAM保存を増やし、短い会話や途中地点の再利用を増やす |
| 常時保持は困るが、一時的なRAMには余裕がある | RAM保存を抑え、必要なサイズのステージングでSSDを活用する |
| 256K付近の状態もSSDに保存・復元したい | 約6〜7GiB級の保存物と、その処理に必要な追加RAMを見込む |
| 複数の長い会話を頻繁に切り替える | 待機時の節約量に加え、保存・復元が続くときのメモリ使用量と待ち時間で評価する |

適切な設定は、最大コンテキスト長だけでは決まりません。普段の会話長、切り替える会話の数、再利用率、保存・復元時に許容できる追加RAMを合わせて判断する必要があります。
