## 1. 今回の目標と実装方針

目標は、Huihui v2のUD-IQ4_XSをGufoで動かし、**ROCm 7.2.3へ戻さず10.1で運用すること**。反復入力で停止する原因も調べ、Gufo側の問題なら修正・貢献につなげたい。

ユーザーが指定した実装の分け方は次のとおり。

1. 未対応の内部形式を扱う共通部品を、既存の計算・命名・実装スタイルに沿って最小限で接続する。
2. その上に、モデルを既存経路へつなぐために必要な対応を加える。

量子化名がIQ4_XSでも、モデル内の全テンソルがIQ4_XSとは限らない。今回のHuihuiにはIQ3_S・IQ4_NLなども含まれており、実際の内部形式に従って対応した。

配布候補のソース・コメント・テスト・説明は英語とし、個人のホームディレクトリなどを埋め込まない。日本語の検証記録は上流ソースの外へ保存する。今回の原因調査でも、診断コードを本体へ組み込んだままにはしていない。

### 回避設定は何をしているか

`AMD_SERIALIZE_COPY=2` は、問題の計算や読み込みを省略する設定ではない。今回使用しているランタイムでは、**コピーやゼロ初期化などのコマンドを投入した後に、完了を待つ**。

この待機で実行タイミングが変わり、停止を回避している。量子化方式を別の形式へ変更したり、IQ3_Sなどの処理を飛ばしたりしているわけではない。

これは暫定的な回避策で、根本原因の修正とは扱わない。現在の構成で機能確認は通ったが、フラグによる性能への影響は正式ベンチでは未測定。

## 4. 停止現象と今回わかったこと

根本原因の調査は、ROCm 10.1・同じ最小対応版Gufo・同じHuihuiを使用した。主な再現要求は、AR、thinking off、単一要求、入力2034トークン、出力16トークン、temperature 0、キャッシュ再利用なし。

設定上のprefill-chunkは512だが、観測されたMMQ呼び出しには2034トークンの形が含まれる。設定値だけから実際のGPU演算の分割を推定しない。

| 確認項目 | 実測・観測結果 | 判断できること／限界 |
|---|---|---|
| 表面上の停止位置 | 993,280 bytes（970 KiB）のlogits読み戻しで完了待ち | コピーが最初の異常とは限らない |
| ROCmの転送ログ | 待機対象の入力依存信号なしでD2H転送を投入し、その完了信号を待ち続ける | 単に直前の計算を待っているだけとは説明し切れないが、先行する異常は除外できない |
| GPUが書く検査結果 | 回避設定なしでは、同期APIが成功しても検査領域が初期値`0xa5`のまま | 正常なGPU書き込みを確認できない。実行失敗・順序・可視性などのどれかは未確定 |
| 同じ検査＋回避設定 | GPUとCPUで248,320個のlogitsの集計とチェックサムが一致し、回答も一致 | 検査器の正常対照は通過 |
| GPU自身の粗い通過記録 | 回避設定なしで2/288個のみ確認 | 最初のIQ3_S処理の初期化後から記録が欠ける条件を観測 |
| より細かい通過記録 | 最初のIQ3_S内部5カーネルを通過し、11/293個まで記録。停止位置が移動 | 診断によるタイミング変化の影響がある。最初のIQ3_Sを原因と確定できない |
| 細かい通過記録＋回避設定 | 293/293個を確認し、回答も一致 | 修正版の診断で正常対照を確認 |
| MMQ一時領域の初期化後だけ待機 | 別々の冷間起動2回で参照回答と一致 | 初期化・一時領域再利用を含む順序が有力な調査対象 |
| データコピー後だけ待機 | 停止が残る | COPY=2の効果をデータ転送の待機だけで説明できない |

診断コードはGPUカーネルや同期処理を追加するため、実行タイミングへ影響する。観測された最初の欠落位置を、そのまま原因箇所と扱わない。

### 改善しなかった条件

- 最後のゼロ初期化後だけ待機。
- IQ3_Sの一方の初期化呼び出しだけ待機。
- ゼロ初期化を単純な独立GPUカーネルへ置き換える。
- direct dispatch無効化。
- AQLの順序バリア最適化無効化。
- 依存信号のCPU側待機。
- 完了信号プールの拡大。
- ハードウェアキューを1本に制限。

`HIP_FORCE_DEV_KERNARG=0`でも停止したが、gfx1151では実質的な配置変更にならないため、配置原因を否定する比較には使わない。

コピーを計算カーネル経由にする設定では、コピー位置を通過しても`!`の誤出力と後続停止が起きた。**この設定は回避策として採用しない。**

## 5. モデルを外した検証

単独HIPプログラムによるコピー、2ストリームとイベント、初期化、負荷カーネル、managedメモリ、複数CPUスレッドからのコピーは通過した。

既存GufoのIQ計算を使う大規模な単独試験も実施した。

| 項目 | 試験内容 |
|---|---|
| 形式 | IQ3_S、IQ4_XS、IQ4_NL |
| IQ3_S / IQ4_XSの行列 | K=5120、M=640 |
| IQ4_NLの行列 | K=640、M=5120 |
| 入力 | 2034トークン、512エキスパート、10選択 |
| 連続実行 | 各形式8回。演算ごとの待機を挟まず投入 |
| 重み配置 | deviceとmanaged＋coarse-grainを別々に検査 |
| 検証 | 最終出力全体を、既存の独立CPU参照データに基づく計算と照合 |
| 結果 | 両方の配置で全形式が通過 |

ただし、これは合成データであり、実際の重み・エキスパート選択分布・約75 GiBの常駐負荷・共有エキスパートとの重なりを再現していない。

**Gufoなしで同じ停止を起こす最小再現器は、まだ作れていない。** また、単独プログラムでもGufoのカーネルを使っている段階では、Gufo側を除外したことにはならない。

## 6. 現時点での結論と未確定事項

確認できたのは、コピー待ちに入る前からGPUの書き込みが確認できなくなることと、待機や診断の挿入によって結果が変わること。

同期成功と実際の書き込みの不一致は、ランタイム・ドライバーの完了通知、順序、メモリ可視性を調べる手掛かりになる。一方で、先行するGufo側の不正アクセスや共有領域の競合がGPU状態を壊す可能性は除外できていない。

したがって、次のいずれも断定しない。

- カスタム実装が原因である。
- Gufo本体は無関係である。
- ROCmまたはWSL／Windowsドライバーの既知不具合である。
- IQ3_S演算そのものが壊れている。
- 読み戻しコピーだけを直せば根本解決する。

共有のID補助領域など、別ストリームで同時使用された場合に確認すべき箇所はあるが、今回の単一要求・ARの停止原因とは確認できていない。

WSLの`dxgkio_escape: -75`や、限定したWindowsイベントの照会からも、今回の停止に対応するドライバーリセットは特定できなかった。これを理由にドライバー原因を否定しない。似た待機スタックの上流Issueも、同一原因とは確認していない。

### 検証記録上の注意

- 初期診断2件は、追加した同期がHIPグラフ記録に干渉して失敗した。失敗記録を保持し、対象をprefill完了箇所へ限定した修正版を別ケースで検証した。
- 初期値0の検査器で件数まで0だった結果は、実際のlogitsが全て0である証拠として使わない。
- 今回はユーザー指定に従い原因調査を優先し、正式な3回性能ベンチは行っていない。演算内の8反復も正式ベンチ8回ではない。
- メモリは主にWSLの時点採取。連続監視のピークではなく、Windows全体・VRAM単独の使用量とも区別する。
- IssueやPRの投稿は行っていない。

## 8. 再開後に進める候補（まだ未実施）

ここから先は、**ユーザーが調査再開を指示してから実施する**。

### ① 実モデルの異常直前のデータと寿命を検査する

実際のエキスパート番号、個数、入出力の配列範囲、テンソルの寸法・stride、一時領域の割り当て・再利用時期、別ストリームとの共有を確認する。

不正アクセスや必要な依存関係の欠落を具体的に観測できれば、Gufo側の修正根拠になる。「待機を足すと動く」だけでは帰属を決めない。

### ② 実際の入力・重み・処理順序を切り出す

合成データではなく、異常が出る実モデルの処理を必要部分だけ切り出し、サーバー全体を外して再現する。共有処理との重なり、メモリ配置、入力分布なども可能な限り維持する。

これにより、サーバー全体の状態が必要なのか、限定した演算とGPU環境だけで発生するのかを絞る。ディスクを圧迫するモデル全体の複製は避ける。

### ③ Gufo固有の処理を段階的に減らす

再現器からGufo固有の計算や一時領域管理を減らし、独立した小さなGPU処理でも同期後に書き込みが欠けるか調べる。

正しいHIPの使い方だけで再現できれば、ROCm・WSL側へ報告できる強い証拠になる。Gufoカーネルを使った再現器が停止しただけでは、この段階へ到達したとは扱わない。

必要になれば、同じ再現器を別の対応環境で照合する。WSLとROCmのどちらに固有かを切り分けるのは、その後の段階。通常運用を7.2.3へ戻す方針ではない。
