Orca IQ4_XS：精度を維持する最適化候補

2026-10-12 JST｜Gufo v0.12.0 / Strata v0.1.42｜調査のみ・未実装

結論

IQ4限定で追加検討する価値がある候補は3系統。公式の高速処理をOrcaの型にもつなぐことを優先し、共通の計算方式・キャッシュ設計・量子化方式は変更しない。今回は調査のみで、実装、GPU試験、速度測定、サービス再起動は行っていない。速度向上や品質合格はまだ実証していない。

「公式ソース以外」は、従来どおりIQ4追加分岐の範囲として整理した。既存の公式ファイルへIQ4限定の分岐や型の実装を追加する必要はある。公式ファイルを一切編集しないという意味なら、以下のカーネル接続案は対象外になる。

調査した現在地

  • 稼働Gufo：公式v0.12.0＋ローカル0c9e454。Orca IQ4_XS、weight-compat off、128K、Orca互換MTP、sessions 1、RAMキャッシュ4GiB。
  • Gufo v0.9.1の4096-token処理・先読み、v0.10.0のPrefill/MTP catch-up改善、v0.11.0のDecode改善、v0.12.0までの更新はソースへ取り込み済み。
  • v0.12.0には新しいキャッシュのアダプター実装が入ったが、サーバーの新方式への全面切り替えはOPENのPR #543。全面切替済みとは扱わない。
  • Strata：公式v0.1.42を確認。v0.1.40.3以降の差分、Strix Halo文書、IQ4のベクトル計算を参照。
  • 調査時点のGufo mainはv0.12.0より2コミット先で、APIのstream受付とdevice_lost検出。これらをIQ4高速化候補とは扱わない。

A：Prefillの共有エキスパートで、既存FP16入力を直接渡す

推奨する最初の候補。 現状では共有エキスパートのSwiGLUをFP32で保存し、IQ4_NL down投影の前でFP16へ変換する。そのために使うx_halfが、後続の分岐エキスパートが必要とする入力を上書きするので、そちらも再変換が必要になる。

公式のQ8経路には、SwiGLUの出力を既存の専用shexp_halfへ直接書き、x_halfを保持する処理がある。しかしDenseF16Routeの型条件はQ8_0のみ。Orcaの共有downはIQ4_NLなので通らない。

IQ4_NLかつ現在からFP16を使うPrefill形状に限定し、SwigluHalfとNativeIq4DenseF16をつなぐ。既存のshexp_half確保を再利用し、Q8用のDenseF16GemmへIQ4重みを渡さない。元から行っている同じ丸めを、書き出す時点へ移す案であり、重みのFP16展開やFP32の長い内積の低精度化ではない。

狙いはPrefill/TTFT。通常Decodeを変更しない。SwiGLU後の全half値、down出力、入力キャッシュの寿命、チャンク分割、独立参照の既定誤差基準を確認する。局所一致だけで採用しない。

根拠：GatedDense（1471行付近）、DenseF16Route（1539行付近）、共有downの呼び分け（2520行付近）。SwigluHalfKernel 1059行、SwigluKernel 1127行。Gufo公式のprivate shared-expert F16 rowsの考え方をIQ4へ限定適用する。

B：Decode/MTPのIQ4 Gate/Upで前処理を再利用し、融合を別段階で試す

B1とB2は別々に実装・評価できる。 公式PR #518でHCの出力からQ8_1入力を直接生成する仕組みが入った。現在のIQ4 MoE DecodeもQ8_1入力を使用しているが、GatedExpertsの再利用・融合条件はQ4_K/Q5_K/Q8_0限定。IQ4_XSでは別途Q8_1を作り、Gate/Upを各1回呼び、その後SwiGLUを呼ぶ。

B1：IQ4専用の事前量子化済み入力の受け口を追加し、ReadyQ8が同一入力・行数・幅の有効な値を保持しているときだけ再利用する。未準備なら現行処理へ戻す。Gate/Upの演算自体は維持。Q8_1の倍率・和・コード・丸めが完全に同じことを先に確認する。

B2：B1とは別に、IQ4_XS専用のGate/Up＋SwiGLU融合と、同じエキスパートを読む行の重み再利用を試す。公式の既存テンプレートを利用できる部分は使うが、呼び出し側のifだけ増やす実装では足りない。型の制限、単行と複数行のディスパッチ、元の内積のグループ分け、SwiGLUの丸め、異常値診断まで確認する。まず単行融合、次にMTP複数行という限定も可能。

これは以前不採用のINT8 Prefillとは違う。現在のDecodeが既に使うQ8_1を同じバイトで再利用する案であり、FP16で動くPrefillをINT8へ変更する案ではない。FP32入力を使うIQ4の通常Dense投影にQ8_1を強制することもしない。

根拠：GatedExperts（1786行付近）、同2014行のmixed_q8_ready_、moe_vector_projection（348行付近）、融合ディスパッチ（882行付近）。公式 PR #518 の約6–7%はQ4_K_XL全体の既存改良の測定値。Orcaのこの候補の予測値には使えない。

C：IQ4_NLのDownを、同じエキスパートの行が近くなる順で処理する

公式PR #518にはDown投影の入力行をエキスパート順へ並べ、元の出力位置へ戻す処理がある。現在のby_expert条件はQ5_1/Q8_0・K=640。IQ4_NLは対象外で、IQ4側のディスパッチはdst_slotsも渡していない。

IQ4_NLのK=640・1行1エキスパートのDecode/MTP処理に限定し、既存の並べ替え量子化と逆写像を接続する。20ブロックという正しいIQ4_NLの行幅を維持する。重みファイルや圧縮重みの配置は変更しない。各出力の加算順序と、MoEの最終合成順をそのまま保つ。

狙いはMTP確認中の重みキャッシュ再利用。エキスパートが重なる入力と、ほとんど重ならない入力の両方で試す。並べ替えの手間で遅くなる可能性があるため、優先度はA/Bより下。同じルーティングへの偏った測定だけでは採用しない。

根拠：by_expert条件（413行付近）、IQ4_NLディスパッチ（870行付近）。

Strataから持ち帰れる考え方と、持ち帰らない変更

StrataのIQ4_NL実装は、重みを読み出す処理と入力への適用を分けて複数入力で再利用し、元の加算順を保つ経路を持つ。この発想はB2/Cの参考になる。ただしGufoにも既に重み再利用や同じ加算順の高速化があり、Strataのカーネル全体を置換する理由にはならない。

  • v0.1.42の高速化見出しには、CUDAで低優先エキスパートの計算を省く方式が含まれる。結果を変えるので不採用。AMDでは既定対象外。
  • gfx12向けINT8融合Prefillはgfx1151への新しい確定改善ではなく、数値の変化もある。過去のINT8不合格を覆す根拠にはならない。
  • CPUへの分担変更、MTP注意窓の縮小、重み/活性値の精度変更は今回の候補に含めない。
  • 転送用固定バッファ・複数GPU・エキスパート入替の改善は、現在のGufoで対象重みをGPUへ置いて使う構成に直接当てはまるとは限らない。
  • TSUM等の発想とGufoの既存DPP化を重複して新しい成果として数えない。

PR #551：n-gram読み込みを32並列から128並列へ変更する未マージの公式PR。現在のローカルngram.cppもkWorkers=32。資料の128並列という記述だけで有効と判断してはいけない。作者のQ4_K_XL試験では新規入力の待ち時間を主に約0.3–0.6秒短縮したが、一部の遅延増加も記録され、Orca/このWSL環境での効果は未測定。IQ4用に二重実装せず、公式の採否を追うのが適切。PR #551

キャッシュの新方式への接続PR #543、エキスパートストリーミングPR #513も共通処理。今回のIQ4限定最適化へ混ぜない。PR #543 / PR #513

採用条件と進める順番

A → B1 → B2 → C。各候補を単独で戻せる差分にし、精度を先に確認してから速度を見る。全候補をまとめる必要はない。

  1. 現行と候補の演算結果・入力形式・端数行・符号付きゼロ・倍率・加算/FMA順を確認する。独立CPU/公式参照の既定閾値を維持する。
  2. 現行GPUとの一致だけで合格としない。以前の1/129行での独立参照不合格を、閾値変更や参照変更で回避しない。
  3. 通過後、同じOrca/MTP・コンテキスト・入力・生成数・キャッシュ履歴で比較する。32K/128Kを各3回の平均と全値で提示。小さな差なら未確定とする。
  4. Decode候補はMTPの各確認幅・採用/棄却・巻き戻し状態、固定履歴の全logits、固定seedと実際の生成を確認する。1行のベンチだけでMTPへの効果を保証しない。
  5. 速度/TTFT/メモリの悪化を隠さず報告し、ユーザーと合意して採用する。長時間の全モデル試験を最初から繰り返さない。

旧い配置改善やFP16重み展開は再提案しない。新候補の速度向上率は、測定するまで未提示。
