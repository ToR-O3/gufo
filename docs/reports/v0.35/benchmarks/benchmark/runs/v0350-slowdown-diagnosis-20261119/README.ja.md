# Gufo v0.35.0 速度低下の切り分け（2026-11-19）

> 履歴資料：本文の採用状況・起動状態・未完了事項は作成当時の記録です。現在の仕様は共通カスタム台帳を参照してください。測定値は再集計せず保持し、個人ホームパスを匿名化しています。生ログ・個人設定は公開対象に含めていません。

対象はQwen3.8 Flash-Next、Unsloth v3.1系 IQ4_XS。11月12日と19日の定例ベンチでは、Gufoの版とモデルファイルの両方が変わった。今回は、同一機で実際のリリース用イメージを一つずつ起動し、11月19日の通常モデルと保存済みHTTP入力を共通にして比較した。エンジンのソースや通常設定は編集していない。

## 3版での再測定

単位はtok/s。Prefillは新しく処理した入力の速度、6件同時は全要求の出力トークン数を最初の送信から最後の応答までの時間で割った値。定例値は従来の外れ値処理後。追加実測は各3回をすべて残し、中央の値を採用した。

| 測定項目 | 定例 v0.34 → v0.35 | v0.34 `319fcdde` | v0.35 Q6_K改修前 `a6a6e491` | v0.35 改修後 `8296d0a4` |
|---|---:|---:|---:|---:|
| 内蔵PLE、32K履歴、AR Prefill | 1,145 → 778 | 1,109.05 | 1,105.62 | 1,110.25 |
| 外部PLE Q8、64K履歴、MTP Prefill | 983 → 724 | 991.94 | 996.07 | 1,001.13 |
| 内蔵PLE、通常文、MTP 6件同時生成 | 70.69 → 60.73 | 60.74 | 58.14 | 63.13 |

各版・各条件でサーバーを起動し直した。Prefillでは同じ接頭辞を準備してから同じ入力を送った。6件同時では正式ハーネスの準備要求と128トークンの生成要求をセットで再生した。主比較の測定対象は計72回答。保存済みの回答本文と、入力・キャッシュ・出力の各トークン数がすべて一致。各セルは一度のサーバー起動で3回を計測しており、再起動間のばらつきまでは推定していない。個々の値と集計（ローカル保管：diagnosis.json）・要求ごとの実測（ローカル保管：results.jsonl）

## 最初のトークンを待つ時間

内蔵PLEのMTPを1件ずつ続けて実行すると、定例の最初のトークンまでのサーバー時間は32.45 → 82.69 ms、待ち行列の計上時間は32.35 → 82.62 msになった。RAMから戻したデータ量は毎回187,351,168バイト、復元処理の中央値は15.08 → 16.70 ms。DFlash2でも最初のトークンは70.72 → 120.70 ms、復元処理は51.27 → 47.01 msだった。

上流の `48aeeee9`（#1183）は、完了した応答を次のターンで継続できるよう、生成済みの位置までキャッシュに保存する。保存が進行中であれば、新しい要求は `ComponentTextCache::Acquire` 内で完了を待つ。診断用コンテナでその待ちを直接計測し、直前の応答からの間隔だけを交互に変えた。

| 直前の応答からの追加間隔 | 保存完了待ちの3実測（ms） | 最初のトークンまでの3実測（ms） | 最初のトークンの中央値（ms） |
|---|---|---|---:|
| 0 ms | 11.38 / 11.36 / 15.60 | 125.72 / 59.53 / 67.69 | 67.69 |
| 600 ms | 0 / 0 / 0 | 38.40 / 57.26 / 50.90 | 50.90 |

追加の600 msは測定開始前の実験操作。6回答の本文と処理量はすべて一致。応答直後に来る次の要求が実際に待たされることを確認した。定例で増えた約50 msのうち何msをこの処理が占めたかは、当時の内部記録からは復元できない。DFlash2での内部待ちは今回計測していない。待機の計測ログ（ローカル保管：controls/2-C-c1-frontier.log）

## 6件同時の生成

定例の18要求を個別に見ると、生成処理は中央値10.64 → 12.32秒、待ち行列は108 → 111 ms、最初のトークンは185 → 193 ms。入力2,040トークンは全件キャッシュから再利用し、各128トークンを出力。v0.35の3回の合計速度は68.34 / 61.10 / 60.37 tok/sで、6要求分のMTP提案数は72 / 384 / 414。v0.34では70.69 / 70.64 / 70.75 tok/s、提案数は72 / 126 / 90だった。

MTPは直近に実測したバッチ処理の時間と、提案が採用される見込みから次の提案数を決める。両版でこの判断コードは同じ。今回の3版比較でも入力と出力が一致したまま提案数が変わった。定例で時間が延びた段階は生成処理まで特定できる。提案数の変化と、各GPU演算そのものの速度変動がそれぞれ何秒を占めたかは未確定。

旧v0.34に11月12日と同じ旧モデルを戻した追加試験でも、53.67 / 64.75 / 59.35 tok/s（中央値59.35）。現行モデルでv0.34をもう一度実行すると63.89 / 59.25 / 59.43（中央値59.43）。後者は18回答のうち1件で本文が異なり、処理トークン数は18件とも一致。この2回目の結果は主比較に混ぜていない。追加試験の生データ（ローカル保管：controls/results.jsonl）

## 長い履歴のPrefill

内蔵PLEの32Kでは、v0.35定例の同日中にもう一つ対照がある。DFlash2比較用に投機生成を切って実行したARは、同じバイナリ・モデル・起動設定で先頭38件のHTTP入力もバイト単位で一致し、32Kの結果は1,102 / 1,135 / 1,116 tok/s。遅かった内蔵PLE表の779 / 777 / 1,091 tok/sと異なる。Q6_K変更が触れるのはMTP提案用の語彙投影で、ARはこの経路を使わない。

外部PLEの64Kでは、両日の各3要求とも65,448トークンをその場で再利用し、新たに処理したのは2,057 / 2,051 / 2,070トークン。RAMやディスクからのキャッシュ復元は全件0 ms。定例の処理時間は2,140 / 2,081 / 2,105 msから2,842 / 2,784 / 2,859 msへ延びた。当時のログには、この約0.7秒をGPU演算とPLE読み込み待ちに分ける情報がない。


外部PLE表の先頭から当時のHTTP入力42件を同じ順に再生すると、64K対象は935.67 / 946.62 / 938.51 tok/sとなった（中央値938.51）。この3件は保存済みの回答・処理量ともに一致。サーバーのPrefillは2,198 / 2,167 / 2,206 ms、要求送信から最初のトークンまでにPLE読み込みの完了を待った時間はそれぞれ約162 / 176 / 191 ms。生成済みキャッシュの保存完了待ちはいずれも0 ms。正式測定時の724 tok/sは、この再生でも再現しなかった。PLE待ちの数字は今回の実測に限る。計測ログ（ローカル保管：controls/3-C-history64.log）

準備を含め42件の回答本文はすべて一致した。うち準備要求1件（ID 85）で、キャッシュから使えた量が当時32,704、今回は14,336トークンだった。起動時に自動決定されたRAMキャッシュ容量も、当時8,623,765,504、今回は8,583,684,096バイトと差がある。容量差と再利用量の因果関係は未確認。今回の比較では、入力と投入順を固定しても途中の内部状態を完全には再現できなかった。

内部の待ち時間は診断用コンテナにだけ観測用ライブラリを読み込み、該当する条件変数の待ちが0.1 msを超える区間を記録した。HTTP計測との対応は同一ホストの単調時計で求めた。これは前景処理がPLEワーカーの完了を待った時間で、読み込みとGPU演算が重なった区間やストレージ装置の総I/O時間を表すものではない。当時のGPUクロック・温度・他プロセスのGPU負荷は確認できず、測定時刻による速度差の発生源は未特定。診断の集計（ローカル保管：diagnosis.json）

## 冷間起動

外部PLEの定例では全体が37.03 → 43.10秒。ローダーの秒単位の時刻によると、読み込み開始からセッション初期化に入るまでが約34秒から40〜41秒に延び、その後は両版とも概ね2〜3秒だった。今回の3版比較は定例の冷間条件を揃えた起動試験ではないため、この内訳からモデル入出力や特定の初期化処理に原因を絞ることはできない。

## 通常運用への復帰

調査終了後、調査前と同じv0.35.0 `8296d0a4` コンテナを再起動。内蔵PLE、共有Q8 MTP、131,072コンテキスト×2セッション、RAMキャッシュ4 GiBの通常設定で、`/ready`、モデル一覧、短い応答生成を確認した。
