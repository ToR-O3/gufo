各回の遅延フラグと比較条件

v0.15の処理時間が対応するv0.14より5%かつ3ms超増えたものを残します。平均で打ち消したり、測り直しで置き換えたりしていません。

  • 32K / 1回目 / decode_s: 21.183 → 22.290 秒（+5.23%）

実行順は1組目v0.14→v0.15、2組目v0.15→v0.14、3組目v0.14→v0.15。各版・各組を新しいプロセスで起動し、32K→128K各16出力tokenの準備実行後、32K→128Kを正式計測しました。準備12件は平均に含めません。ロード時間・OSファイルキャッシュ性能は測定対象外です。

修正済み入力は前回とバイト一致。24件の資料、正解JSON、Decimal計算と厳密一致条件を維持しました。thinking off、temperature 0、seed 42、出力上限4096（自然終了）、同時1要求、sessions 2、MTP adaptive 1〜7、RAM cache 4GiB、cache_prompt=false、prefill-chunk指定512、Vision有効。128K入力の回答領域確保のため、両版ともcontext 262144。実処理chunkやsnapshot時間も各usageに保存しています。

旧版は当時の保存済みバイナリ、新版は稼働中と同じバイナリ。同じイメージ・依存ライブラリ・マウントで実行し、旧版の再ビルドや独自最適化の追加はしていません。

新版32Kの1回目には最長0.725秒のtoken間隔があり、クライアント側でも約0.721秒の間隔を確認しました。旧版2回目の遅さも含め、原因は分離できていません。ログのキャッシュ拡張記録では、v0.14の拡張イベントはいずれも正式計測より前でした。v0.15には同じイベントの出力がないため、ログの不在を内部確保がなかった証拠にはしていません。

測定の限界

同じ課題を2種類の長さに配置した各3回の結果であり、全用途の改善率ではありません。WSLから温度・GPUクロックを取得できず、Windows側負荷の影響は完全には排除できません。電源プラン・負荷・メモリ・各要求のキャッシュ内部状態を保存しています。

通常設定へ復帰済み

元のGufoコンテナ・v0.15バイナリ・Config・HostConfig・マウントが一致。context 131072、sessions 2、RAM cache 4GiB、thinking off、MTP adaptive 1〜7、Vision有効で再起動し、応答と実MTPを確認しました。モデルファイルに変更はなく、一時コンテナは削除済みです。
