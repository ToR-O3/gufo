GPUメモリ確保方式の単体試験

2026-10-20 / Radeon 8060S・Strix Halo / WSL・Docker / Strataと同じROCm 7.14.1

4 MiBずつ確保すると専用GPUメモリ63.760 GiB、容量63.829 GiBの約99.89%を使用。

表示上は63.8 / 63.8 GiB相当。完全な100.000%ではない。専用側をほぼ埋めた後、追加分が共有側へ回る動作を確認した。

有効だったのは hipMalloc の確保単位を小さくする方法。管理メモリへ切り替える方法は、この環境では共有メモリを増やした。推論計算・本体ソース・通常起動設定は変更していない。

確認した範囲

各方式は同じStrataイメージ、同じGPU・ROCmで実行。GPU上で各確保領域の全域へ0x5aを書き込み、同期後、各領域の先頭・中央・末尾512バイトを読み戻した。全ての成功した試験で一致。全領域の全バイト検証や実モデルの出力・速度検証は行っていない。

主比較ではhipMallocとhipMallocManaged＋CoarseGrainを同じ8 GiB/4 GiB単位で比較。管理メモリ方式は24 GiBまでで、専用0.798 GiB・共有24.964 GiBとなった。CPU→GPUのコピーで埋める8 GiB試験でも同じ傾向だった。その後、通常確保の単位を256 MiB、16 MiB、4 MiBへ変更して改善を確認した。各条件は1回の測定で、256 MiBは48 GiBまでの予備確認と64 GiBの確認を実施。

容量不足で無理に押し込む試験は行っていない。管理メモリは24 GiBで次の追加分の余裕がなくなり拡大を終了。小分け通常確保は専用側が増えたため、64 GiBまで到達できた。

GufoとStrataの実装との関係

Gufoの対象リビジョン9b076b1では、モデル重みをテンソルごとに確保し、総重みサイズと空きヒープ量から通常確保または管理メモリを選ぶ。管理メモリにはCoarseGrainを指定する。常に管理メモリを使う実装ではない。

StrataのExpertCache::open_sizedはスロット容量を合計し、HIPでは通常の大きな一括確保に進む。今回の結果は、この確保粒度の違いが専用／共有の配置に大きく効くことを示す。ドライバー内部で切り替わる根本条件までは未特定。

本体へ取り込むには、連続領域とオフセットを前提としたキャッシュのアドレス管理を確認する必要がある。単にhipMallocを管理メモリAPIへ置き換える案は採用しない。今回の4 MiB分割はGufoの正確なテンソルサイズを再現した試験ではなく、確保粒度を切り分けた試験。

失敗・制限・解放確認

最初の試験は8 GiB確保後にWindowsの計測が失敗し、中止。比較には使っていない。再試験のcomparison-v2は完了。途中でCodexのWindows／WSLパス不整合が再発したが、保存済み結果を接続復旧後に読み直した。AMDの統合メモリ資料の詳細ページ再取得にも失敗し、その未取得ページを結論の根拠にしていない。

各コンテナ終了時にlibdxcoreのアンロード警告が出た。hipFreeは成功し、専用・共有メモリのベースライン復帰を別途確認。管理メモリ解放直後はWindowsの物理メモリ回収が遅れ、その後回復した。4 MiB試験後は専用0.712 GiB・共有0.943 GiBへ復帰し、Windows空き31.288 GiB。

コミット量は実際の物理RAM使用量とは異なる。専用GPUメモリ使用率とGPU演算使用率も別の指標。本試験は容量・配置を測定しており、演算使用率100%を目標にしたものではない。

通常のStrata：元の構成で再起動し、healthy・loaded=trueを確認。128K・Orca IQ4_XS。Gufoは停止のまま。本体への小分け確保の適用は未実施。再起動時の別測定では専用約45.99 GiB・共有約30.23 GiB。これは従来方式の通常Strataであり、上記の単体試験結果とは別。
