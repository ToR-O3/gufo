# v0.37の断続的な待機増加の調査（2026-11-27）

> この文書は各作業段階の記録です。最終判断（2026-11-27）はv0.37の採用保留・外部化見送り、通常利用はv0.36 main、キャッシュ上限4 GiBです。本文の当時の状態・計画・測定値は維持しています。ローカル生ログは同梱せず、公開用コピーでは利用者ホームパスを匿名化しています。

## 結論

今回捕まえた遅延の主な増加箇所は、ROCmのGPU完了待ちである。CPUがOSに実行させてもらえず待機する時間の増加が、数百msの遅延を説明する結果ではなかった。v0.36にも同じ変動があり、Stages移行によるCPU処理増加を主因とする証拠はない。

原因の「層」はGPU／ドライバーの完了待ちまで特定できた。GPU自体の速度変動、ドライバーの処理・通知、外部のメモリ帯域・電力・GPU負荷のどれが待機を増やすかは未確定。「外部負荷が原因」「v0.37の最適化不足」と断定する証拠は得られていない。約1〜2%の差まで否定する試験でもない。

## CPUは何を実行していたか

WSLでperf_event_openを使い、Gufo各スレッドのユーザーモードCPU実行位置を約1ms間隔で採取。通常コンテナの権限は変えず、追加試験コンテナだけCAP_PERFMONを付与した。記録にlost/errorはない。実プロセスのmapsとnmシンボルを照合した。

CPUサンプル中、次のGPU完了通知待ちループがv0.36で85.2%、v0.37で83.1%を占めた。

rocr::core::BusyWaitSignal::WaitRelaxed(...)

CPUが眠る待ちではなく、CPU上で完了通知を繰り返し確認する待ちである。そのためCPU使用率が高くても、Gufoのモデル処理がCPUで重くなったことを意味しない。

v0.37の追加プロファイルでは速い回48.26 tok/sから遅い回43.82 tok/sに変動し、この待機関数のサンプル数は4233→5006に増加。v0.36にも同じ傾向がある。サンプル数はCPU実行時間の統計的な観測で、GPU実行時間の直接計測ではない。

追加プロファイルは速度順位を評価する用途には使わない。v0.36側では計測中にシンボル抽出処理が重なっており、診断用の証拠としてのみ扱う。正式な速度比較は上の4プロセスの計測値と前回の非プロファイル値を参照する。

## 外部負荷について

最初の4プロセスではWindowsプロセス別CPU時間を並行記録した。遅い回だけ外部CPU負荷が一貫して跳ね上がる関係は確認できなかった。Linux CPU pressureも記録したが、これはWSLの仮想CPUがホスト側で停止する時間やGPU・メモリ帯域の競合を網羅しない。

WindowsのGPU利用率は追加プロファイル中にスポット確認しただけで、全測定区間と対応した時系列ではない。複数GPU・複数プロセスが存在するため、この一時点の値から同じGPUの競合や原因を断定しない。

外部負荷の因果関係を確定するには、同じGPUのホスト側スケジューリング・クロック等との時刻対応、または外部負荷を統制した対照が必要。無関係なアプリは停止していない。今回の調査は「待機場所を特定、最終的な誘因は未確定」とする。

## 失敗と復旧

- 最初のWSL接続はE_ACCESSDENIED。権限付きの読み取りで復旧。
- 最初の試験はコンテナの /usr/bin/env の参照先が使えず起動前失敗。invalid-base1-envに保持し、実在するNixのenvを使用して再試験。
- sched_schedstats設定はなく、実行待ち時間をその機能では採取できなかった。
- 追加のWSL接続がWSAETIMEDOUTになったが、進行中の測定は完走。最小接続の成功後に通常の接続も復旧。WSL再起動なし。
- デフォルト試験コンテナ内のperf_event_openはEPERM。CAP_PERFMONを付けた試験コンテナで成功。
- 前回と同様、GPUカーネル個別実行時間の直接計測は未取得。
